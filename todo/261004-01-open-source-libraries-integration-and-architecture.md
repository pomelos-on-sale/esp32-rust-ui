# 架构与规划指南: 嵌入式图形底层自研与开源库复用边界

- **所属模块**: `pomelo-gfx`, `iced-pomelo-gfx`, `pomelo-apps`
- **目标平台**: ESP32-S3 (Xtensa Dual-Core LX7 @ 240MHz, 8MB Octal PSRAM) + 480×480 RGB565 AMOLED 面板
- **创建日期**: 2026-10-04
- **状态**: 指导原则与待办规划 (Guidelines & Proposed)

---

## 一、 背景与工程原则：避免重复造轮子

在现代软件工程与嵌入式系统开发中，**“尽量避免重复造轮子（DRY & Reuse）”** 是降低维护成本、减少边界缺陷、保证系统稳定性的最高准则。

本项目既包含底层的 2D 光栅化引擎（`pomelo-gfx`），又承接了上层完整的声明式 UI 框架（`iced`）。本文档系统性地梳理：
1. **为什么在光栅化核心环节不得不自研轻量级引擎？**（根本物理与硬件限制）
2. **当前系统实际上已经深度依赖并复用了哪些开源巨人？**
3. **后续功能演进中，哪些模块应优先引入成熟开源库？**

---

## 二、 为什么被迫自研 `pomelo-gfx`：硬件瓶颈与生态断层

Rust 开源生态中有不少优秀的 2D 图形库，但在**微控制器驱动高分辨率彩色屏幕**这个特定交集上，存在严重的生态断层：

### 2.1 桌面级开源 2D 库的不可行性（以 `tiny-skia` 为例）

Iced 原生配套的 CPU 渲染器是 `iced_tiny_skia`（基于 `tiny-skia`）。然而，它无法在 ESP32-S3 上达到可用帧率：

| 指标 | 通用桌面库 (`tiny-skia`) | 自研直绘引擎 (`pomelo-gfx`) | 差异原因 |
| :--- | :--- | :--- | :--- |
| **显存布局** | 强制 **RGBA8888**（32位深，预乘 Alpha） | 原生 **RGB565**（16位深） | 面板物理接口为 16-bit QSPI，无需中间全屏缓冲 |
| **显存占用** | $480 \times 480 \times 4 \text{ B} \approx \mathbf{921.6\text{ KB}}$ | $480 \times 480 \times 2 \text{ B} \approx \mathbf{460.8\text{ KB}}$ | 节省整整一半显存，大幅减轻 PSRAM 压力 |
| **传输开销** | 必须每帧在 PSRAM 中做一次全屏 RGBA8888 $\to$ RGB565 格式降维转换 | 绘制直接写在物理帧缓冲区上，**0 转换开销** | 避免了每帧近 1.4MB 的 PSRAM 读写总线争用 |
| **实测填充耗时** | 约 **4.4 µs / 像素** | 约 **0.12 µs / 像素** | **~36 倍性能差距**，直接决定系统是 5 FPS 还是 60 FPS |

### 2.2 嵌入式开源 2D 库的局限性（以 `embedded-graphics` 为例）

Rust 嵌入式最知名的 `embedded-graphics` 专为资源极度匮乏的单片机（如 STM32、nRF52 黑白屏/小彩屏）设计：
* 其核心架构是**单像素拉取迭代器（`pixel_iter`）**，没有分层渲染树（Layer Tree）、矩阵变换（Transform Stack）、任意凸四边形光栅化与抗锯齿剪裁栈；
* 无法支持 `iced` 所依赖的高级特性：**局部重绘差分（Damage Diffing）**、平滑贝塞尔曲线、任意角度渐变与矢量字形遮罩。

### 2.3 结论
自研 `pomelo-gfx` 是因为**开源界缺乏“直接在 RGB565 上光栅化、又具备现代 UI 局部重绘与矩阵变换能力”的轻量库**。自研是出于对 **240MHz 主频 + SPI PSRAM 带宽** 的物理妥协。

## 三、 当前架构已复用的开源资产

尽管最底层的 RGB565 像素扫描线循环是自研的，但上层的高难度数学与核心基础完全基于开源库构建：

```text
┌────────────────────────────────────────────────────────┐
│                   iced_widget / iced                   │  <-- 开源生态: 响应式状态管理、UI树、Flex 布局
└───────────────────────────┬────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────┐
│                    iced-pomelo-gfx                     │  <-- 桥接层: 局部损伤追踪 (Damage)、绘制命令录制
└─────────────┬────────────────────────────┬─────────────┘
              │                            │
┌─────────────▼──────────────┐ ┌───────────▼─────────────┐
│  cosmic-text / swash (开源) │ │       kurbo (开源)       │  <-- 开源数学库: 字体排版、矢量曲线细分
└─────────────┬──────────────┘ └───────────┬─────────────┘
              │                            │
┌─────────────▼────────────────────────────▼─────────────┐
│                       pomelo-gfx                       │  <-- 自研核心: Direct-to-RGB565 像素级光栅化
└────────────────────────────────────────────────────────┘
```

1. **几何与曲线数学 (`kurbo`)**：
   * 贝塞尔曲线求值、弧线近似、包围盒求解均由 Google 字体团队主导的开源库 [`kurbo`](https://crates.io/crates/kurbo) 提供，绝不自造曲线数学。
2. **文本排版与字形渲染 (`cosmic-text` & `swash`)**：
   * 复杂的 Unicode 双向文本排版（BiDi）、OpenType 字体解析、字形 Subpixel Coverage 蒙版生成，直接使用开源顶流库。
3. **UI 框架与运行时 (`iced`)**：
   * 完全兼容 Iced 标准 API，业务应用可以直接按标准的 Iced 程序编写。
4. **经典图像学算法标准**：
   * 渐变抗色带采用的 Bayer 8×8 阈值矩阵是图像学经典标准序列，算法逻辑严格遵循数字信号量化与误差分散理论。

## 四、 后续功能演进与开源库复用路线图 (TODO)

后续在扩展多媒体、更丰富特效和性能调优时，应严格遵循复用优先原则：

### 4.1 感知均匀色彩空间与平滑渐变 (`palette`)
- [ ] **现状**: 当前 `LinearGradient` 采用简单的 RGB 浮点线性插值，在人眼视觉感知上不同明度区域的过渡并非严格均匀。
- [ ] **优化目标**: 引入轻量、支持 `no_std` 的开源库 **[`palette`](https://crates.io/crates/palette)**。
- [ ] **复用方式**:
  - 利用 `palette::Oklab` 或 `palette::LinSrgb` 进行渐变插值计算，使人眼察觉到的色彩过渡更加均匀平缓；
  - 插值完成后再将感知色彩映射为 RGB565 抖动输出。

### 4.2 高效嵌入式图像与流式解码 (`qoi` / `image`)
- [ ] **现状**: 目前图标和背景图多采用预烘焙的 RGB565 / Alpha 蒙版二进制。
- [ ] **优化目标**: 引入开源的 **QOI (Quite OK Image)** 解码器（如 [`qoi`](https://crates.io/crates/qoi) crate）。
- [ ] **优势**:
  - QOI 具有媲美甚至超越 PNG 的无损压缩率；
  - 解码速度比 PNG 快 20~50 倍，内存占用极小，支持逐行边解压边直接灌入 RGB565 帧缓冲。

### 4.3 乐鑫硬件加速与矢量指令集 (`esp-dsp`)
- [ ] **现状**: 像素颜色混合（Alpha Blending）目前采用纯标量整数运算，未能充分释放 ESP32-S3 双核 128 位 PIE 向量指令（SIMD）的性能。
- [ ] **优化目标**: 评估并引入乐鑫官方开源的 **[`esp-dsp`](https://github.com/espressif/esp-dsp)** 库。
- [ ] **复用方式**:
  - 借用其成熟的 16 位数组定点点乘、批量移位汇编算子，加速大面积图层透明度混合与抗锯齿遮罩合成。

### 4.4 复杂矢量图形填充与拓扑细分 (`lyon`)
- [ ] **现状**: `pomelo-gfx` 目前只支持凸四边形（Convex Quad）填充，对于带自相交或空洞的任意凹多边形只能描边。
- [ ] **优化目标**: 当业务出现复杂的非规则多边形填充需求时，引入开源的 **[`lyon`](https://crates.io/crates/lyon)** 进行路径三角剖分（Tessellation）。
- [ ] **复用方式**: 将复杂的矢量路径转为顶点三角形网格，然后复用现有光栅化管线。

## 五、 自研与复用的决策核查清单 (Decision Checklist)

在考虑编写任何新的底层模块前，必须逐项核对以下检查清单：

1. **生态检索**: Crates.io 或 GitHub 上是否有成熟的、已解决该问题的 crate？
2. **内存兼容**: 该 crate 是否支持 `no_std`？是否强制要求分配全尺寸的 32 位 RGBA 缓冲区？（若强制绑定 RGBA，则不能用于帧缓冲直绘核心）
3. **计算复杂度**: 算法是否高度依赖大型查表或双精度浮点？（ESP32-S3 仅有单精度硬件 FPU）
4. **代码规模**: 该 crate 是否引入了庞大的间接依赖树？是否会导致 Flash 固件膨胀过大？
5. **提取复用**: 如果整个 crate 过于厚重，是否可以直接提取其核心数学算法/常量表（保持开源许可证兼容的前提下）以减少依赖？
